# 비동기 / 멀티스레드 - 언제, 어떻게 쓰는가

## 핵심 판단 기준: CPU-bound vs I/O-bound

| 유형 | 특징 | 스레드 풀 크기 공식 |
|------|------|-------------------|
| CPU-bound | 연산이 많음 (암호화, 압축, 이미지 처리) | CPU 코어 수 + 1 |
| I/O-bound | 대기가 많음 (외부 API, DB, 파일) | CPU 코어 수 × (1 + 대기시간/연산시간) |

> **면접 포인트**: CPU-bound에 스레드를 너무 많이 만들면 컨텍스트 스위치 비용이 오히려 손해

---

## 비동기를 쓰는 이유

동기: 총 소요시간 = 각 작업 시간의 합  
비동기: 총 소요시간 = 가장 오래 걸리는 작업 하나

---

## 언제 쓰는가

**적합한 경우**
- 외부 API 호출, DB I/O, 파일 I/O 등 **10ms 이상** 걸리는 작업
- 서로 **의존성이 없는** 병렬 처리 가능한 작업

**부적합한 경우** (오버헤드가 이득보다 큼)
- 단순 인덱스 DB 조회, 캐시 조회, 단순 계산
- 트랜잭션 경계가 중요한 작업 (롤백 범위 관리 복잡)

## Spring에서 비동기 구현

### ThreadPoolTaskExecutor 설정

```java
@Configuration
@EnableAsync
public class AsyncConfig implements AsyncConfigurer {

    @Bean
    public Executor asyncExecutor() {
        ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
        executor.setCorePoolSize(5);
        executor.setMaxPoolSize(10);
        executor.setQueueCapacity(25);
        executor.setKeepAliveSeconds(60);
        executor.setRejectedExecutionHandler(new ThreadPoolExecutor.CallerRunsPolicy()); // 중요
        executor.setTaskDecorator(new MdcTaskDecorator()); // MDC 전파
        executor.setThreadNamePrefix("async-");
        executor.initialize();
        return executor;
    }
}
```

**RejectionPolicy 종류** (큐가 꽉 찼을 때)
- `AbortPolicy` (기본): 예외 던짐
- `CallerRunsPolicy`: 호출한 스레드가 직접 처리 (속도 조절 효과)
- `DiscardPolicy`: 조용히 버림
- `DiscardOldestPolicy`: 가장 오래된 작업 버리고 재시도

### MDC 전파 문제와 해결책

비동기 스레드는 부모 스레드의 `ThreadLocal`을 상속하지 않음  
→ 요청 IP, 계정명, 트레이스 ID 등이 새 스레드에서 사라짐

```java
public class MdcTaskDecorator implements TaskDecorator {
    @Override
    public Runnable decorate(Runnable runnable) {
        Map<String, String> contextMap = MDC.getCopyOfContextMap();
        return () -> {
            try {
                if (contextMap != null) MDC.setContextMap(contextMap);
                runnable.run();
            } finally {
                MDC.clear();
            }
        };
    }
}
```

### @Async 주의사항: Self-Invocation 문제

```java
// 같은 클래스 내에서 호출하면 AOP proxy를 타지 않아 @Async가 무시됨
@Service
public class MyService {
    public void call() {
        this.asyncMethod(); // 비동기로 실행되지 않음!
    }

    @Async
    public void asyncMethod() { ... }
}
```

해결책: 별도 클래스로 분리하거나 `ApplicationContext`에서 빈을 꺼내 호출

### @Async + @Transactional 조합 문제

`@Async`는 새 스레드를 만들고 `@Transactional`은 트랜잭션을 스레드에 바인딩  
→ **부모 트랜잭션이 자식 비동기 작업에 전파되지 않음**  
→ 비동기 메서드에서 예외가 나도 부모 트랜잭션이 롤백되지 않음

## CompletableFuture 체인 메서드

| 메서드 | 용도 |
|--------|------|
| `thenApply` | 결과값 변환 (동기) |
| `thenCompose` | 연속 비동기 작업 (flatMap) |
| `thenCombine` | 두 작업 병렬 후 결과 합치기 |
| `allOf` | 전부 완료 대기 |
| `anyOf` | 가장 빠른 결과 사용 |

```java
// anyOf - 나머지 스레드는 자동 취소되지 않음, 명시적 cancel 필요
List<CompletableFuture<String>> futures = List.of(cf1, cf2, cf3);
CompletableFuture.anyOf(futures.toArray(new CompletableFuture[0]))
    .thenAccept(result -> {
        futures.forEach(f -> f.cancel(true)); // 나머지 명시적 취소
    });
```

### 에러 처리

```java
// exceptionally: 예외 발생 시 대체값 반환
future.exceptionally(ex -> {
    log.error("비동기 처리 실패", ex);
    return defaultValue;
});

// handle: 정상/예외 모두 처리
future.handle((result, ex) -> {
    if (ex != null) { /* 롤백, 정리 */ return fallback; }
    return result;
});
```

> **주의**: 에러를 처리하지 않으면 예외가 조용히 사라짐

## Java 21 Virtual Thread

```java
// Virtual Thread: OS 스레드 1개에 수백만 개 가상 스레드 매핑
// I/O 대기 중 OS 스레드를 점유하지 않음 → I/O-bound 작업에 탁월
ExecutorService executor = Executors.newVirtualThreadPerTaskExecutor();
```

**기존 ThreadPool과 차이**
- 기존: I/O 대기 중 OS 스레드 블로킹 → 스레드 풀 소진 위험
- Virtual Thread: I/O 대기 시 캐리어 스레드(OS 스레드) 반납 → 수백만 동시 요청 처리 가능

**주의**: CPU-bound 작업에는 효과 없음, `synchronized` 블록 안에서 I/O 하면 carrier thread pinning 발생

## 모니터링 지표 (스레드 풀 튜닝)

| 지표 | 의미 | 조치 |
|------|------|------|
| Active Thread Count | 현재 실행 중 | maxPoolSize와 비교 |
| Queue Size | 대기 중 작업 수 | 지속 증가 → maxPoolSize 증가 |
| Rejection Count | 거부된 작업 수 | 빈번 발생 → 구조 재검토 |
| Task Execution Time | 평균 처리 시간 | 증가 → 로직 최적화 먼저 |

## 단점 정리

1. **에러 전파 누락**: 명시적 핸들링 없으면 예외 소멸
2. **MDC/ThreadLocal 전파 안 됨**: TaskDecorator 필수
3. **트랜잭션 경계 복잡**: @Async + @Transactional 조합 주의
4. **유지보수 복잡**: 코드 흐름 추적 어려움
5. **불필요한 비동기**: 컨텍스트 스위치 오버헤드가 이득보다 클 수 있음
6. **MSA 분산 트랜잭션**: Saga 패턴 등 별도 전략 필요

---

## 결론

> **은탄환은 없다.** I/O-bound + 의존성 없는 병렬 작업 + 충분한 처리 시간(10ms+) → 비동기 효과적  
> 먼저 **로그/트레이스로 병목 확인** → 의존성 없는 것부터 순차 전환 → **부하 테스트로 풀 크기 튜닝**
